# lumos_workflow (Resource)

A Lumos workflow: an ordered list of steps. Approval, provisioning and deprovisioning workflows run only once they're bound to an app or entitlement, which is a separate step.

For approval templates and chains, see the [approvals guide](../guides/approvals.md).

## Example Usage

```terraform
# An approval chain with one approval stage assigned to a group. It runs
# through an approval template that references it, once that template is
# bound to the app or one of its entitlements.
resource "lumos_workflow" "it_approval" {
  app_id      = lumos_app.deploy_dashboard.id
  type        = "approval-chain"
  name        = "IT approval"
  description = "One approval stage, assigned to the IT group."
  steps = [{
    step = "approval_task"
    inputs = jsonencode({
      stage_number = 1
      assignees    = [{ uuid = "<group id>", type = "group" }]
    })
  }]
}
```

## Schema

### Required

- `name` (String) A name for this Workflow.
- `steps` (Attributes List) The ordered steps of the workflow. (see [below for nested schema](#nestedatt--steps))
- `type` (String) The kind of workflow. must be one of ["approval", "approval-chain", "entitlement-provisioning", "entitlement-deprovisioning", "account-provisioning", "account-deprovisioning"]; Requires replacement if changed.

### Optional

- `app_id` (String) UUID of the app this workflow belongs to. Leave it out for a workflow not yet tied to an app. Once the workflow has an app, set when it's created or by binding it, Lumos can't clear or change it, so the config must set it. Requires replacement if changed.
- `description` (String) A description of this Workflow.

### Read-Only

- `id` (String) A UUID identifying this Workflow.

## Writing steps

* **`step`** is the step's identifier. `GET /v1/workflow-steps?app_id=<app id>&type=<workflow type>` lists the steps available to a workflow of that type on that app, with the inputs each one accepts.
* **`inputs`** is written with `jsonencode`, in the form Lumos reads back, or every plan shows a change:
  * durations in ISO 8601, for example `"P1D"` or `"PT12H"`;
  * numbers, such as `stage_number`, as numbers;
  * assignees as `{ uuid = "<id>", type = "<user | group>" }`, or `{ label = "<attribute>", type = "custom_attribute_definition" }` for a custom attribute;
  * other workflows, groups and users by their IDs;
  * branch conditions with every attribute and value as a `{ label, value }` object (see the [approvals guide](../guides/approvals.md#branch-conditions)).
* **Changing `type`**, or `app_id`, replaces the workflow.
* **`app_id` follows the config, and can't be cleared once set.** Leave it out for a workflow not yet tied to an app. Binding such a workflow gives it the app it's bound to, and from then on the plan fails until the config sets `app_id` to that app. If you know the app, set `app_id` when you create the workflow.
* **`description`** can be left out, but can't be `""`.
* **A workflow runs only once it's bound** to an app or an entitlement. An approval chain runs through the approval template that references it.

## Limitations

* Placeholder steps can't be imported and applied.
* A chain can be used by only one workflow. Lumos refuses a template that references a chain another workflow already uses.
* A chain a template stops referencing is kept, so it stays managed by its own `lumos_workflow` resource.

## Import

In Terraform v1.5.0 and later, an [`import` block](https://developer.hashicorp.com/terraform/language/import) can be used with the workflow's ID:

```terraform
import {
  to = lumos_workflow.it_approval
  id = "<workflow id>"
}
```

The [`terraform import` command](https://developer.hashicorp.com/terraform/cli/commands/import) can also be used:

```shell
terraform import lumos_workflow.it_approval "<workflow id>"
```
